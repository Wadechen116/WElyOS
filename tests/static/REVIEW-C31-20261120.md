# C3.1：PMM 保留底線與並行查詢審查

2026-11-20，Codex。基準 063969f 加 Claude 第52步工作樹。產品以補丁交 Claude 整合；未提交。

## 結論

底線判斷先拒絕 n=0 或 n>nfree，再以 nfree-n < floor 判斷，與位圖更新、refs初始化在同一把 pmm_lk 裡。
普通單頁、多頁及間接經由它們的配置均預設受保護；應急入口明確 opt-in，目前未見產品呼叫者。
啟用點在排程器啟動前，usable 一次取樣；min(max(usable/8,1024),usable/2) 不下溢，少於2頁明確拒絕開機。

本輪未找到一般配置突破底線的情況。找到一個同步問題：pmm_free_count 無鎖讀 nfree，而並行配置/釋放持鎖寫它；
新增 pmm_reserve_refusals 無鎖讀 floor_refusals，而持鎖配置會更新它。
這影響診斷與測試的同步契約，不能據此說實際配置的鎖內底線判斷已失效。

交付 `patches/pmm-stats-lock.patch`：三個查詢都在 pmm_lk 下取單一值快照；git apply --check 通過。
floor_pages 啟用後不變，不宣稱它當前有並行寫者；統一查詢契約以涵蓋 enable。
pmm_total_pages/mem_start 仍是 boot 後不變的值。核對現有查詢呼叫者未在 pmm_lk 內重入；pstate→PMM等既有鎖順序未改。
每個getter獨立取樣，不宣稱跨多個getter能取得同一時刻的整體快照。

## 獨立探針

`probe_pmm_floor.py` 編譯完整、實際的 kernel/pmm.c，不重寫配置/釋放演算法。
僅以 pthread mutex 代替 IRQ/spinlock，預先建立合成位圖、refs、頁對齊 arena；每次解鎖驗證位圖/refs/nfree/hint一致與普通配置的底線。
不執行 pmm_init、不驗 boot保留區、實體MMU或硬體中斷。

- exhaustive：總頁數1–8、全部使用中/空閒位圖、全部可行底線、請求0至總量+2與SIZE_MAX，共25,851組。
  配置位置與獨立first-fit模型比對；失敗時 bitmap/refs/nfree/hint 完全不變（允許診斷拒絕計數增加）；釋放後恢復。
  合成已使用頁皆有owner；不包含boot保留頁的refs=0情況。主機為64位元，不把有限狀態測試寫成所有整數寬度的證明。
- boundaries：無底線boot配置、啟用0/超額失敗、重複啟用失敗、floor+1批次拒絕、floor單頁拒絕、共享refs最後owner才釋放、應急耗盡/歸還、floor=free。
- parallel：八執行緒×1,000輪從floor+2競爭兩頁，每輪恰好一個成功、七次拒絕；全部釋放後恢復。
  另160,000次隨機批次配置/釋放，並行查詢free與refusals，最後恢復全部256頁。
- getters：明確驗證三個查詢的加鎖快照契約；原版失敗，修後通過。TSan另提供實際資料競爭證據。
