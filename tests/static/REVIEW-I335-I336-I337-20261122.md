# Independent review: I-335 / I-336 / I-334 / I-337

Date: 2026-11-22

## Scope

- Read-only review of commit `6eb3e44` (I-335 runtime sweeps and I-336 prepaid
  page-table bitmap).
- Read-only review of commit `be44791` (I-334 lost-wakeup fix).
- Read-only review of `scratchpad/mountfi.patch` from Claude's shared-memory
  assignment.
- Added and ran `tests/host/proc/probe_i337_wake.c`, a bounded algorithm model

- No product code, QEMU run, or full regression was part of this review.

## Findings

### I-336: prepaid page-table bitmap

The bitmap, `pt_tickets == popcount(prepaid)` invariant, anon slot numbering,
fault consumption, fork settlement, and legacy-table refund path are internally
consistent in the reviewed code. `anon_recommit_test()` covers repeated untouched
commit/release, eventual touch, legacy refund, and destroy cleanup.

The missing narrow regression is a failed `vm_space_commit_anon()` due to quota,
followed by a quota increase and retry. It should compare the bitmap, ticket
count, domain accounting, and PMM reservation before and after the failed
attempt, then confirm the retry succeeds. Claude reported that this regression
is being added.

### I-335: allocation-failure sweeps

Commit `6eb3e44` adds runtime sweeps for mmap/sbrk, pipe I/O, UDP open/receive,
and WFS create/check paths. The documented remaining gap is boot-time allocation
failure in `wfs_mount`, `bcache_init`, and mount-time `wfs_check(1)`; the existing
runtime injector cannot reach those paths.

Two FAILSWEEP reliability issues were independently found in the committed
implementation: `fsw_take()` ignores `fsw_quiesce()` timeout, and baseline
convergence continues after timeout while treating samples above baseline as
stable. Snapshot collection should abort on timeout and require consecutive
equal samples. Claude reported that these fixes are in progress.

The reviewed `mountfi.patch` addresses the boot-time gap with a memory-backed
disk and checks allocation errors, heap/PMM balance, unmounted state, unchanged
disk bytes after failure, and successful remount. The repeated-mount lock
initialization, per-mount state reset, and `wfs_format()` error propagation
changes look correct. Its `dirty` case tests an unclean marker and
`wfs_check(1)` allocation paths; it does not introduce actual dirty metadata or
corruption, so it does not independently verify recovery from damaged state.

### I-334: signal lost wakeup

The `user_return_check()` change routes either pending or interrupted state
through `deliver_signal()` under `sched_lk`, the same lock used to enqueue the
signal. If a signal arrives after the fast checks, the interrupt state remains
visible to `thread_sleep()` under that lock. The sleep invariant hook checks the
same signal state while locked. No blocking defect was found in the reviewed
change. The one-shot delay injection targets a process rather than a thread;
the current test has only one parent thread, so this does not invalidate it.

### I-337: CPU0 sleeper-wakeup dependency

The host model passes for 1/2/4/8 CPUs and both scan orders when all CPUs share
one monotonic clock; each sleeper is dequeued exactly once. With CPU0-only
scanning, a deadline at tick 5 wakes at tick 8, 32, 100, 101, or 256 when CPU0
is paused for those durations. An ideal any-CPU scanner wakes at tick 5.

The architecture timer APIs publish CPU0's deadline to other CPUs, so
`timer_ticks_real()` can extrapolate while CPU0 is delayed. The host model shows
an AP can wake a sleeper due in 5 ticks while global `ticks` is frozen. The
catch-up is capped at 100 ticks, though; a sleeper due 105 ticks after the
frozen global count remains pending through a longer CPU0 stop. Moving the scan
to APs therefore improves bounded delays, but does not cover an indefinitely
stopped CPU0. Either define the supported delay bound or revise global time
recovery so another CPU can advance time beyond the catch-up cap.

The I-337 probe also models two independent-clock candidates for a CPU0 failure:

- **A: shared hardware counter to ticks.** With a 16-bit 10 kHz counter, a
  1 kHz tick, and a fixed epoch near counter wrap, AP scans wake sleepers due
  at +100/+200/+300 ticks during a 300 ms CPU0 stop. The modeled delays are
  0 ms (at most one AP timer interval in a real implementation, before adding
  dispatch, lock, and counter error).
- **B: absolute counter-derived candidate plus CAS max.** A forced stale
  candidate race (+5 wins before +4 retries) leaves time at +5; the 300 ms AP
  run publishes 300 monotonic tick advances and wakes each sleeper once.

Both candidates assume all CPUs observe one synchronized monotonically
advancing hardware counter and AP timer interrupts continue. The wrap test
crosses one 16-bit counter wrap; the sample interval remains shorter than one
full wrap. A raw modulo counter cannot distinguish zero wraps from one full
wrap, so longer intervals need a rollover extender. The CAS model validates
clock publication only; per-tick side effects such as RT accounting need their
own serialized cursor or must remain separate from the CAS update. Cross-CPU
counter synchronization, timer delivery, lock latency, and kernel behavior are
not established by this host model.

## Verification

`probe_i337_wake.c` compiled with GCC warnings-as-errors and AddressSanitizer /
UndefinedBehaviorSanitizer, then ran successfully. This validates the stated
model only; it does not validate architecture timer synchronization or kernel
behavior. No QEMU or full regression was run by Codex.

## Step 68 review (commit `661c223`)

Read-only review of the I-339/I-340, clksync, scheduler, and memhog changes:

- **I-340 committed map:** no concrete defect found in the reviewed paths. The
  bitmap is allocated and charged with the address space, commit/release
  updates run under `vm_lk`, faults check commitment before consuming tickets,
  fork copies the bitmap, and allocation-failure/destroy paths return the
  bitmap pages and KOBJ charge.
- **I-339 aligned PMM API:** the current 512-page caller is a power of two and
  the chunk allocation/free path looks consistent. The public helper uses a
  bit mask but does not reject or document non-power-of-two `align_pages`;
  those values would not have general alignment semantics. `n > nfree` also
  increments the `floor_refusals` diagnostic even when the actual reason is
  exhaustion.
- **Memhog watchdog:** completion reporting detects a worker that exits before
  its final report, but the initial ready handshake still has a pipe EOF hole.
  The parent blocks reading the shared `rep` pipe inside the fork loop while
  retaining `rep[1]`; if that child exits before its initial status, the
  parent's writer prevents EOF and the host timeout remains the only escape.
  A per-child ready pipe (parent closes its writer immediately after fork),
  separate from the shared completion pipe, preserves the sequential ready
  decision while making early child death observable.
- **Scheduler latency test:** `lat_hog_running == nh` proves every hog ran at
  least once, not that hogs simultaneously occupy distinct CPUs. If the test
  depends on all non-target CPUs being busy, it needs a stronger occupancy
  barrier or direct evidence; this is a reliability concern, not a reproduced
  failure.

The `starve_scan()` future-timestamp guard is correct for catch-up ticks:
`ready_since` can equal the published final tick while the scan is processing
an earlier intermediate tick, and the guard avoids unsigned subtraction
underflow. The RT release/deadline paths already compare against their nominal
release values and showed no analogous issue. The host counter-sync probe now
uses the same strict whole-intersection-within-tolerance acceptance rule as
`kernel/clksync.c`; its overlap-only predicate remains solely as a contrast.

This review did not modify product code or run QEMU/full regressions.
