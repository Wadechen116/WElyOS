## 結論與適用範圍

本輪未證實新缺陷。i386 的 set 使用 lock cmpxchg8b，EDX:EAX 為比較/載入值，ECX:EBX 為目標值，ZF 未成功便重試；
初次猜測的普通 64 位元讀取即使撕裂，也不會直接發布，CAS 會驗證它。記憶體與 flags clobber 存在。
get 亦用 locked CMPXCHG8B，故需要可寫記憶體；只核對本專案可寫的頁表/測試頁，不把它宣稱為一般 readonly load。
頁表配置 4KB 對齊，項目 8 bytes，未見不對齊項目；arch_mmu_init 在使用前檢查 CX8。

參考 [Intel SDM Vol. 2A，CMPXCHG8B/CMPXCHG16B](https://www.intel.la/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-vol-2a-manual.pdf)，3-183 至 3-184。
本報告的硬體語意判斷是依上述文件及反組譯推論，並非真實 PAE walker 壓力實驗。

目前 vm.c 有 **13 個 arch_pte_set 呼叫點**（不是交接留言的25個），含未發布下層表填入、parent發布、中間表、leaf map/unmap、fork降權及COW。
其餘 memset(table_alloc)、memcpy(vm_space_create) 寫入當時尚未發布的表。普通 PTE 讀取仍在既有 VM 鎖契約下；
本次沒有把 atomic set 推論成整個VM、TLB或AArch64 break-before-make已驗證。
TLB shootdown/ASID與釋頁次序沒有因兩處helper替換而改動，既有實機限制仍須保留。

## 三筆 fork_table baseline

舊函式 token SHA256：45799144fc9f2887ed85d0d8753108b8f025d57573af19b6bf7164eae33cd27d。
新函式：9f7051f594473444899763a1f7bb260c1f49bb563e3621bd1875966b5c68b1da。
將以下兩個 arch_pte_set 陳述還原為舊賦值後，函式 token hash **完全等於舊 hash**：

- arch_pte_set(&t[i], arch_pte_leaf(pa, flags, 0)) → t[i] = ...
- arch_pte_set(e, arch_pte_leaf(pa, flags, 0)) → *e = ...

另外人工核對 caller 仍傳 MMU_LEVELS-1，各架構 MMU_LEVELS=3；只有 level>0 會遞迴且每次減1，level0不遞迴。
所以只接受這個深度有界的遞迴例外，不接受全函式任意安全性。
